# 박사님께 별도로 공유드리는 메모 (내부용, rev. 2)

윤태입니다. 영문 서면과 별개로, 코드를 두 차례(정밀 감사 + 적대적 재검증) 검증하면서 확인된 사항 중 박사님께서 미리 알고 계셔야 할 것들입니다. 두 번째 검증은 "첫 감사가 틀렸을 가능성"을 전제로 전부 재실행했는데, 핵심 발견 10건이 모두 재현 확정됐고 수치 몇 개만 정밀화됐습니다. 리뷰 답변은 서면 방향대로 진행하면 되고, 아래는 그 과정에서 정리해야 할 내부 사항입니다.

## 1. Fig 4B 재현 불가 + Rhonchi 임계값 결함 — 사실상 하나로 연결된 이슈 (가장 급함)

**Fig 4B**: 제 로컬 산출물을 두 차례에 걸쳐 전수 탐색(confusion matrix CSV 57개 + classification report 전부, Development/OPERA 실험 포함)했는데, Fig 4B의 수치(Healthy 89 / Wheezing 85 / Crackle 87 / Rhonchi 94 / Non-breathing 65)와 ±3%p 이내로 일치하는 결과물이 **하나도 없습니다**. 최종 학습 스크립트는 성능 지표를 저장하지 않는 버전이라 재현 근거가 남아 있지 않습니다.

**Rhonchi 임계값**: 최종 배포된 thresholds.json에서 Rhonchi 임계값이 Infinity입니다. 원인은 확정했습니다 — 최종 run의 validation 분할(3녹음)에 Rhonchi 샘플이 0개라 ROC 임계값 계산이 무한대를 반환했고 그대로 저장됐습니다. 이 때문에 현재 배포 앱에서는 임계값 반영 판정에서 Rhonchi가 절대 선택되지 않습니다(171개 val 윈도우 시뮬레이션에서 Rhonchi 선택 0회).

**두 이슈의 연결**: 최종 run의 val에는 Rhonchi가 0개인데 Fig 4B에는 Rhonchi 94%가 있습니다. 즉 **Fig 4B는 최종 run의 분할에서 나올 수 없는 그림**이고, 다른 분할/다른 평가에서 생성된 것입니다. **보내주실 코드 세트에 Fig 4B를 만든 평가 스크립트나 결과 파일이 있는지 확인 부탁드립니다.** 없다면 R2-6 대응으로 돌리는 재평가 결과로 Fig 4B를 재산출해야 하는데, 이때 **기존 ≥85% 수치가 그대로 재현된다는 보장은 없습니다** (참고로 배포 모델을 현 val에서 재계산하면 47.9%가 나오지만, 이 val 자체가 3녹음짜리 퇴화 분할이라 이 수치도 일반 성능은 아닙니다). 재산출 수치가 달라지면 그림 교체 + 본문 "at least 85%" 문구 + Table S3 조정이 연쇄됩니다. 이 부분이 이번 리비전의 가장 큰 리스크라 먼저 말씀드립니다.

재학습 시에는 임계값 계산에 유한성 가드(샘플 부족 클래스는 기본값 폴백)를 넣고, 배포본 모델 파일도 교체하겠습니다.

## 2. 참가자 수 — 3개 층위 정리 필요 (R2-5 답변 전 필수)

숫자가 세 층입니다: **43명 등록**(Methods L503-505: healthy 5 + 환자 38) → **"38명 환자가 학습에 사용"**(본문 L357) → **실제 파이프라인 투입은 24녹음/참가자 21명/윈도우 1,368개**(재검증으로 확정, healthy 포함 수치).

원본 38개 wav 중 14개가 특성 추출에 못 들어갔는데, 사유는 두 갈래입니다: WEBSS 계열 11개는 호흡 구간 주석이 없어서, KP002·KP012(2세션)는 **주석 JSON의 세션 접미어(_1/_2)와 wav 파일명이 안 맞아 세그먼트 추출이 빈 결과**를 낸 것으로 보입니다. R2-5가 세트별 정확한 수를 요구하므로, 답변 표는 실측 수치로 만들고 본문 문구도 맞춰야 합니다. 리뷰어가 43/38/실사용 수치 사이의 관계를 되묻지 않도록 세 층위를 답변에서 한 번에 정리하는 게 안전합니다. (KP002/KP012가 단순 매칭 버그였다면 고쳐서 데이터를 살릴 수도 있는데, 그러면 학습 데이터가 바뀌므로 재학습과 함께 결정할 사항입니다 — 의견 주세요.)

## 3. 업데이트 주기 — 앱을 0.5초로 통일 권고

본문(L156-157)은 0.5초마다 업데이트, 배포 앱은 1.0초, 오프라인 추론 스크립트(tetho_softmax_export.py)는 실행값 0.5초입니다(이 스크립트는 주석에는 "1s hop"이라고 적혀 있어 내부적으로도 어긋나 있습니다 — 정리하겠습니다). Fig 4C 트레이스가 이 스크립트로 생성됐다면 0.5초 해상도 산출물이라, **앱을 0.5초로 맞추는 쪽이 본문·그림 수정 없이 일관성을 만드는 방향**입니다. 연산량은 문제 안 됩니다(윈도우당 64차원 벡터 1회 추론). 레이턴시 답변(R2-8)은 이 결정 후에 쓰겠습니다. 다른 의견 있으시면 알려주세요.

## 4. 서술 정리 사항 (말씀하신 프레임으로 처리)

패딩부터 말씀드리면, 수정 대상 문장은 본문 L348-350의 "with padding applied to shorter segments"입니다. 실제 구현은 패딩 없이 2초 미만 꼬리를 폐기하고, 짧은 이벤트는 0.5초 홉의 중첩 윈도우가 커버하는 구조입니다. 말씀하신 대로 "추가 검토 결과 이 표현이 더 정확하다" 프레임으로 Methods 문구를 교체하겠습니다 (구체 문안은 영문 서면에 넣어 두었습니다).

윈도우 근거로 쓰는 수치도 이번에 정밀화했습니다. 주석 구간에서 재계산해 보니 호흡 phase의 88.2%가 2초 미만(중앙값 약 1.2초)이라, 예전부터 쓰던 88.8%는 88.2%로 통일하겠습니다. 오버랩 배수도 학습/오프라인은 4×(0.5초 홉)인데 현재 앱은 2×(1.0초 홉)여서, 답변에서 오버랩을 근거로 쓰려면 §3의 홉 통일이 여기서도 전제가 됩니다.

분류 구조 서술은 본문 안에서 서로 어긋나 있습니다. L158-160은 breathing 판별 후 4클래스로 가는 계층 구조처럼 썼고, L374-376은 플랫 5클래스의 사후 그룹핑으로 썼는데, 구현은 후자(플랫)입니다. 앞부분을 뒷부분에 맞춰 통일하겠습니다.

마지막으로 본문 L385-386(HR/BR 임계 초과 시 알림)과 L394(확신도 70%)에 해당하는 로직이 현재 앱에는 없습니다. HR/BR 계산 자체가 없고 UI 카드는 정적 "--"이며, 임계값 판정 결과는 계산 후 사용되지 않습니다. R1-4 대응으로 알림 집계 규칙을 구현할 때 함께 정리하거나, 아니면 해당 서술을 완화하는 방향 중에서 정하면 될 것 같습니다.
